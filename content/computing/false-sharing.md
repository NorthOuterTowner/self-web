为并行计数器做改造时遇到一个反直觉的结果：把单个共享计数器换成「每线程一个计数器」之后，总吞吐反而下降了约三倍。代码里没有互斥量，没有原子竞争写同一地址，看起来完全无共享。

## 问题结构

```c
// 每个线程只写自己的 slot，看似无竞争
struct counters { uint64_t slot[NUM_THREADS]; };
// slot 之间间隔 8 字节，8 个 slot 恰好落在同一条 64 字节缓存行上
```

缓存一致性的粒度不是字节，而是**缓存行**，通常 64 字节。只要两个核写的地址落在同一行，这一行就会在它们的私有缓存之间反复失效与搬运。硬件看不到「它们写的是不同变量」这件事。

## 定位过程

1. 先确认不是调度问题：绑核之后现象依旧，排除线程迁移。
2. 统计 LLC 与 L1 的 miss 比例，发现 L1 写 miss 异常高，而总内存带宽很低 —— 数据量不大却一直在搬。
3. 观察 MESI 状态相关事件，确认缓存行在 Modified 与 Invalid 之间高频震荡，这是伪共享的指纹。
4. 把每个 slot 填充到独占一条缓存行，吞吐恢复并随核数线性增长。

```c
struct padded_counter {
  uint64_t value;
  char pad[64 - sizeof(uint64_t)];
} __attribute__((aligned(64)));
```

> [!NOTE]
> 填充会放大内存占用。计数器这种少量、高频写的结构值得填充；成千上万个实例的结构体则要权衡，否则换来的是 cache 容量压力。

## 可迁移的判断

判断是否值得怀疑伪共享，有两个比较便宜的信号：一是扩核之后吞吐不增反降，二是内存带宽很低但 L1 写 miss 很高。两者同时出现时，先去看热点变量的地址分布，比继续读业务逻辑有效。

更一般的教训是：**无锁不等于无共享**。把「共享」的定义从变量粒度换成缓存行粒度，很多并行代码的性能行为才开始讲得通。
