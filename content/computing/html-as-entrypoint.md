传统的前端构建里，入口是一个 JS 文件。打包器从它开始遍历 `import`，产出若干 chunk，然后由插件把 script 标签注入模板。HTML 在这条链路的末端，它不参与依赖分析，只是被改写的对象。

把 HTML 提到入口位置，等于承认一件事：决定一个页面需要加载什么的，本来就是 HTML。`link`、`script`、`img`、甚至 favicon，都是真实的依赖边。

## 资源图的根节点换了位置

以 HTML 为根时，打包器要先解析标签，收集所有本地引用，再分别按类型进入对应的处理管线：模块脚本走 JS 图，样式表走 CSS 图，图片和字体走 asset 管线并拿到带哈希的文件名。最后写回 HTML 的是同一次遍历的结果，而不是另一套插件猜出来的。

```html
<!-- 入口本身就声明了全部依赖 -->
<link rel="icon" href="./mark.svg" />
<script type="module" src="./frontend.tsx"></script>
```

一个直接的好处是 favicon 这类「不在 JS 图里」的资源也会被正确哈希和搬运。过去要靠额外的 copy 插件处理，现在它和其他依赖没有区别。

## 部署前缀是同一个问题的另一面

资源路径的前缀（public path）在两种模型下的影响范围不同。JS 为入口时，前缀主要作用于运行时的 chunk 加载逻辑；HTML 为入口时，它必须同时改写三处：HTML 里的标签属性、CSS 里的 `url()`、以及 JS 里由 asset import 产生的字符串常量。

> [!NOTE]
> 部署到形如 `user.github.io/repo/` 的子路径时，只要前缀少改了一处，页面就会白屏，而且控制台只给出 404，不会提示是前缀问题。

验证方式很朴素：构建后直接读产物，确认三类文件里的路径都带上了前缀。比起信任配置，读一遍输出更快。

```bash
bun build ./src/index.html --outdir=dist --public-path=/repo/
# 然后确认 dist/index.html 与 bundle 里的 asset 路径都带 /repo/
```

## 代价

- 多页应用需要显式列出每个 HTML 入口，不能再靠一个 glob 配置带过。
- HTML 里的内联脚本处理规则需要额外约定，否则容易出现「一部分代码被打包、一部分没有」的割裂。
- 开发服务器必须自己处理路由回退，否则刷新子路径会 404；这件事在 JS 入口模型里通常由框架插件默认做掉了。

结论不是哪种更好，而是入口的选择决定了「谁来定义依赖」。HTML 入口把这个权力交还给了文档本身，相应地也要求你更清楚自己的部署形状。
