我们首先来讨论如何实现这个需求，随后探讨这种技术方案是否可行，具有哪些缺点。

## 实现需求

我们假设架构为 Vue + FastAPI，假设硬件设备的IP地址为164.17.65.34，实际应用位置为127.0.0.1:5000。可以认为，我们的需求是在浏览器地址栏输入 <http://164.17.65.34/> ，浏览器自动访问 <http://127.0.0.1:5000/> ，并保持看起来是 <http://164.17.65.34/> 不变。

首先需要明确的一点是，浏览器本身并不存在这种能力。

对于一个普通的HTTP请求：<http://164.17.65.34/psat/>，浏览器会解析出：

```text
Host: 164.17.65.34
Port: 80
Path: /psat
```

随后直接向<http://164.17.65.34/>发起TCP连接。也就是说，对于浏览器而言，地址栏中的IP地址本身就决定了请求应当发往哪里。因此单纯依靠Vue路由、FastAPI路由或者前端代码，是无法截获这一过程的。如果希望实现用户输入：<http://164.17.65.34/psat/>，实际访问<http://127.0.0.1:5000/psat/>, 那么必须存在一个位于浏览器与网络之间的中间层，在浏览器发出请求后对其进行改写。因此整个架构会演变为下面的格式：

```text
Browser -> Local Proxy -> 127.0.0.1:5000 -> PyVISA -> 164.17.65.34
```

在这里，浏览器访问的是设备IP。但设备IP对应的HTTP请求会被本地代理劫持，并转发至本地运行的Web应用，而本地应用再使用PyVISA连接真正的设备，这样对于最终用户来说，从视觉上看，用户仿佛正在访问Radio。

### 实现代理脚本

代理层的职责非常简单，首先识别目标是否为设备IP，保存原始设备IP，随后将请求转发到<http://localhost:5000>，并在过程中保持浏览器地址不变。最简单的实现方式之一是使用 mitmproxy，例如：

```python
from mitmproxy import http
RADIO_NETWORK = "164.17."
def request(flow: http.HTTPFlow):
    if flow.request.host.startswith(RADIO_NETWORK):
        radio_ip = flow.request.host
        flow.request.headers["X-Radio-IP"] = radio_ip
        flow.request.host = "127.0.0.1"
        flow.request.port = 5000
```

当用户访问<http://164.17.65.34/psat/>时代理实际执行：<http://127.0.0.1:5000/>，并将原始IP放入：`X-Radio-IP: 164.17.65.34`供后端读取。

### 启动代理

假设本地应用运行于：<127.0.0.1:5000/>，则可以通过：

```bash
mitmdump \
  --listen-port 8080 \
  -s radio_proxy.py
```

启动代理。随后启动浏览器：

```bash
msedge.exe \
  --proxy-server=http://127.0.0.1:8080
```

此时浏览器的网络结构变成：

```text
Browser -> 127.0.0.1:8080 -> 127.0.0.1:5000
```

但浏览器并不知道这一过程，因此地址栏依然显示<http://164.17.65.34/>

### 后端获取设备IP

对于Vue而言，访问api的过程与普通Web应用并没有任何区别，FastAPI则可以通过请求头获取原始设备IP，随后通过PyVISA连接设备：

```python
import pyvisa
rm = pyvisa.ResourceManager()
radio = rm.open_resource(
    f"TCPIP0::{radio_ip}::inst0::INSTR"
)
```

## 方案的合理性

软件工程中有一个非常重要的原则，地址应该表示资源的位置，而不是资源的参数。对于一个普通的Web应用：<http://github.com/>, 含义是访问GitHub服务器。对于：<http://localhost:5000/>, 含义是访问本地Web应用。

而在本方案中：<http://164.17.65.34/>实际上表达的是使用<http://164.17.65.34/>作为参数，这是十分明显的语义混乱。因为地址栏显示的内容与真正被访问的服务器已经不一致了。当一个新的开发人员接手项目时，他很可能认为<http://164.17.65.34/>上面运行着一个Web服务。而实际情况却是<http://127.0.0.1:5000/>才是真正提供页面的服务器。这种认知偏差会显著增加系统维护成本。

## 更符合工程实践的方案

更符合现代Web架构习惯的实现通常是<http://localhost:5000/radio/164.17.65.34/>或者<http://localhost:5000/?radio_ip=164.17.65.34/>,也无需本地代理、流量劫持、浏览器特殊配置或者额外的进程，因此维护成本也更低。

## 总结

从技术角度来说，使浏览器地址栏中的设备IP不直接对应设备本身，而是打开本地Web应用，是完全可以实现的。其核心原理并不是浏览器或者Vue本身具备这种能力，而是在浏览器与网络之间引入了一层代理。同时把原始IP作为参数传递给后端，再由PyVISA完成设备连接。然而这种方案本质上属于一种网络层Hack，其能够提升某些特定场景下的使用体验，却破坏了URL本身的语义一致性。因此在实际工程中，更推荐将设备IP作为业务参数，而不是作为应用访问地址进行伪装。
